Code Verification of Physics-informed Neural Networks (PINNs)¶

This notebook is part of the FDA SimEval toolbox, https://github.com/OSEL-DAM/SimEval

Introduction¶

Physics-informed neural networks (PINNs) are a recently-developed, novel approach for solving ordinary or partial differential equations (ODEs, PDEs) which are receiving a lot of research interest (Raissi, 2019,Karniadakis, 2021). PINNs are an alternative to the long-established finite difference, finite volume and finite element methods, and use neural networks to approximate the solution of the governing equations. In a PINN formulation, a neural network is designed to take in the independent variables, such as spatial coordinates $\mathbf{x}$ and time $t$, and output the solution $u$ of the equation. The neural network serves as the numerical approximation of the solution field of the ODE/PDE.

Unlike conventional neural networks in which the loss function is minimized by comparing the network's output $u$ to a ground truth value, PINNs incorporate the governing equations and boundary conditions into the loss function. The loss function is designed to compute how well the governing equations and boundary conditions are satisfied across a range of 'collocation points', i.e., specific locations in the domain where the network is evaluated; a loss function of zero indicates the governing equations and boundary conditions are perfectly satisfied at the collocation points. For example, for a PINN solving the 1D problem solved in the code verification notebook (PdeCodeVerification.ipynb), $u_{xx} = f$, $u(0)=0$, $u_x(1) = g$, the loss function could take the form: \begin{equation} \frac{1}{N_c}\Sigma_{i=1}^{N_c} \left(u_{xx}(x_i) - f(x_i)\right)^2 + u(0)^2 + (u_x(1) - g)^2 \end{equation} where $x_i$ are the collocation points. The neural network takes in a single input $x$ and provides a single output $u$. The network is evaluated at each collocation point to compute the loss, using symbolic differentiation for computing the derivative terms. Training using the standard back-propagation algorithm optimizes the parameters of the network to minimize the loss.

This approach combines data-driven learning with physics-based constraints. While the efficiency benefits of PINNs remain unclear and traditional methods may generally be faster (Grossmann, 2024, Zhongkai, 2024), PINNs could potentially offer value in situations requiring simultaneous fitting of data and solving of the governing equations, among others (Raissi, 2019).

As with traditional methods (e.g., finite element, finite volume, finite difference), it is crucial to ensure that PINNs are implemented correctly, which means performing code verification to confirm their accuracy and reliability. However, there is relatively little in the literature on code verification for PINNs. While there are papers that apply MMS to PINNs (e.g., Grossmann, 2024, Shin, 2020), approaches and challenges in performing end-to-end code verification following the approach recommended by ASME V&V40 2018 for high-risk applications have not been extensively explored.

Aims¶

This notebook builds upon the PDE code verification notebook which provided a workflow for performing MMS that adhered to the highest level of rigor in the "numerical code verification" credibility factor of ASME V&V40 2018. Here, we apply and adapt that workflow for a PINN solver, highlighting steps that differ from the FEM case due to PINN structure or theory. Convergence analyses are performed to assess performance of two PINN solvers, one solving a static 1D diffential equation and one solving a time-dependent 2D PDE. A PINN-specific verification strategy is proposed and demonstrated.

Below we use deepxde to solve the same MMS problem of the code verification notebook. In contrast to the finite element method, for which the numerical scheme was characterized through one key numerical parameter, $h$, the following parameters all impact the PINN:

  • Number of layers. More layers improve the network’s ability to capture the solution, at increased computational cost and risk of overfitting.
  • Number of neurons in each layer. The implemented PINN solvers use a fixed number of neurons per layer. More neurons improve the network’s ability to capture the solution, at increased computational cost and risk of overfitting.
  • Number of collocation points. These are the locations at which the network evaluates the governing equation. In general, collocation points could be randomly sampled once and then held fixed, randomly sampled anew in each epoch (iteration), or cover the domain uniformly, among other options.
  • Number of epochs. In each epoch (also called iteration), the neural network performs a forward pass over all the collocation points to compute the loss, and then updates the network's trainable parameters based on the backpropagated gradients. The number of epochs determines how many times the network iterates over the set of collocations points.
  • Learning rate. This defines the size of the steps the optimizer takes when updating the network's weights. If the learning rate is too high, the optimization may become unstable, while too low of a learning rate could result in slow training convergence.

The first PINN-based solver in the toolbox is a function solve_1d_elliptic_PINN. This is deepxde-based code for solving $u_{xx}=f$ on [0,1], $u(0)=0$, $u_x(1)=g$. Below this function is imported and the code is displayed in case of interest to readers unfamiliar with the basic process of PINN solves. The interface to this solver allows the user to set various parameters and the impact of these on the solution will be explored below. In particular, the user can set the number of collocation points, number of layers and neurons, and number of epochs. The train_distribution parameter controls the distribution of the collocation points (pseudo means collocation points are randomly sampled; an alternative is uniform for a fixed uniform grid of collocation points). The learning rate is initially 0.001, and, if learning_rate_decay is True, is slowly reduced as training progresses, which is a common approach in PINNs to avoid excessive fluctuation around a local minimum when training.

As well as the collocation (training) points, DeepXDE also creates a set of 100 test points and outputs the loss evaluated at these test points during training. If use_best_test_loss is True, the solver will return the network associated with the smallest test loss. If not the final network after the last epoch will be returned.

solve_1d_elliptic_PINN also takes in a random number generator seed parameter, to allow the user to control reproducibility and assess stochastic effects. Results should be reproducible across runs on the same hardware/software environment if the seed is fixed. Below the code in solve_1d_elliptic_PINN is printed:

def solve_1d_elliptic_PINN(rhs_func,                  
                           boundary_condition_value, 
                           num_output_points = 101,  
                           num_colloc = 20,
                           num_layers = 2,
                           neurons_per_layer = 20, 
                           num_epochs = 10000,
                           train_distribution = "pseudo",
                           use_best_test_loss = True,
                           learning_rate_decay = True,
                           seed = None):
    """
    Solve u_xx = f(x) on [0,1], u(0)=0, u_x(1)=g, using a physics-informed neural network (PINN), using
    the DeepXDE library.

    Parameters
    ----------
    rhs_func : function
        The function f(x), should take in one input and provides one output
    boundary_condition_value : scalar
        The value g
    num_output_points : int, optional
        The number of points to provide the solution at. The default is 101.
    num_colloc : int, optional
        Number of collocation points (training points). The default is 20.
    num_layers : int, optional
        Number of layers in the neural network. The default is 2.
    neurons_per_layer : int, optional
        Number of neurons per layer (same in all layers). The default is 20.
    num_epochs : int, optional
        Number of epochs (iterations), default 10000
    train_distribution : string, optional
        How the collocation points will be distributed. Will be passed to dde.data.PDE(). Options
        include "uniform" or "pseudo" (default, randomly sampled)
    use_best_test_loss : boolean, optional
        Saves and restores the best performing weights, i.e., the weights for the iteration that provided 
        the lowest test loss. Defaults to True. 
    learning_rate_decay : boolean, optional
        If True, applies a learning rate decay schedule during training, which can improve stability and reduce
        optimizer variance at later stages. Defaults to True.
    seed : int, default None
        If set, will be used as seed for randon number generation. Set to enforce reproducibility (results should be identical for fixed hardware). 
        See comments in code for how this is implemented - have to do more than just deepxde.config.set_random_seed(seed)  
  


    Returns
    -------
    x : numpy array
        Uniform grid of x values (size based on num_output_points)
    u : numpy array
        Solution at x values
    soln_info : dict
        Dictionary with the following entries
          - 'loss_train' Training points loss (PDE component) for the final solution
          - 'loss_test' Test points loss (PDE component) for the final solution
          - 'colloc_points' - array of collocation points
          - 'resid_at_colloc' - PDE residual at the collocation points
          - 'x_dense' - dense set of 10000 x values across the domain
          - 'resid_at_x_dense' - PDE residual at those x values (so can see if PDE residual is high between collocation points)
    """

    # The following is needed to enforce reproducibility. First, we call deepxde.config.set_random_seed() which will pass the seed to
    # the relevant functions for tensorflow, numpy, random. 
    # However, there is known DeepXDE initializer-seeding bug issue (May 2026) where Keras initializers are created upon initial import 
    # and therefore before the user seed is set. This leads to the user seed being neglected in weight initialization if the following line is called below 
    #   net = dde.nn.FNN(layer_size, activation, "Glorot uniform")
    # Different sessions would end up using different initial weights and therefore different results. 
    # Using the following variant ensures reproducibility across sessions.
    #   glorot_initializer = tf.keras.initializers.glorot_uniform(seed=seed)
    #   net = dde.nn.FNN(layer_size, activation, glorot_initializer)
    # https://github.com/lululxvi/deepxde/issues/2086
    # (Note: another fix to ensure reproducibility across sessions is to call "import random; random.seed(0)" before importing tensorflow but then user can't control the seed)
    if seed is not None:
        dde.config.set_random_seed(seed)  


    # define the PDE to be solved
    def pde(x, u):
        u_xx = dde.grad.hessian(u, x)
        return u_xx - rhs_func(x)

    # function defining the left boundary
    def boundary_left(x, on_boundary):
        return on_boundary and dde.utils.isclose(x[0], 0)
    
    # function defining the right boundary
    def boundary_right(x, on_boundary):
        return on_boundary and dde.utils.isclose(x[0], 1)

    # set up DeepXDE problem          
    geom = dde.geometry.Interval(0, 1)
    bc_l = dde.icbc.DirichletBC(geom, lambda X: 0.0, boundary_left)
    bc_r = dde.icbc.NeumannBC(geom, lambda x: boundary_condition_value, boundary_right)

    data = dde.data.PDE(geom, pde, [bc_l, bc_r], num_colloc, 2, num_test=100, train_distribution=train_distribution)

            
    # set up network
    layer_size = [1] + [neurons_per_layer] * num_layers + [1] # resolves to, e.g., [1, 20, 20, 1] if num_layers=2 and neurons_per_layer=20
    activation = "tanh"

    # See comments at top near dde.config.set_random_seed(seed)  
    glorot_initializer = tf.keras.initializers.glorot_uniform(seed=seed)
    net = dde.nn.FNN(layer_size, activation, glorot_initializer)
    
    model = dde.Model(data, net)
    
    # if learning_rate_decay is true, set up for learning rate to decrease
    if learning_rate_decay:        
        model.compile("adam", lr=0.001, decay=("inverse time", 1000, 0.5))
    else:
        model.compile("adam", lr=0.001)

    # if use_best_test_loss is true, set up so weights are saved each time the test loss is minimized
    if use_best_test_loss:
        best_model_cb = InMemoryBestModel()
        losshistory, train_state = model.train(iterations=num_epochs,callbacks=[best_model_cb])  # add e.g., display_every=500 to change how often the InMemoryBestModel CallBack saves the best loss
        # restore best perfomring model
        best_model_cb.restore_best_weights()
        final_loss_test = best_model_cb.best_value
        final_loss_train = best_model_cb.loss_train_at_best_loss_test
    else:
        losshistory, train_state = model.train(iterations=num_epochs)
        final_loss_train = train_state.loss_train[0]
        final_loss_test = train_state.loss_test[0]
    
    # compute soluntion on gridpoints
    x = np.linspace(0,1,num_output_points).reshape(-1,1)
    u = model.predict(x)
    
    x_dense = np.linspace(0, 1, 10000).reshape(-1,1)

    # collect other info to be returned
    soln_info = dict({'loss_train':final_loss_train,
                      'loss_test':final_loss_test,
                      'colloc_points':data.train_x_all,
                      'resid_at_colloc':model.predict(data.train_x_all, operator=pde),
                      'x_dense':x_dense,
                      'resid_at_x_dense':model.predict(x_dense, operator=pde)
                      })
    

    return x, u, soln_info

Step 5: Error norm¶

In the code verification notebook we discussed how the appropriate norm for characterizing the numerical error depends on the theoretical results available for the method. For example, for finite elements the error is naturally measured using the integral $L_2$ or $H^1$ norms. For PINNs, while error theory does exist (Shin, 2020, DeRyck, 2022,Mishra, 2023), there is a lack of theory providing practical expected rates of convergence.

Therefore, we can choose error norms based on other considerations. Two possibilities are the discrete $l_2$ and $l_\infty$ norms: \begin{align*} \|u - u_\textrm{true}\|_2 &= \frac{1}{N^{1/2}}\left(\Sigma_{i=1}^{N} \left(u(x_i) - u_\textrm{true}(x_i)\right)^2\right)^{1/2}\\ \|u - u_\textrm{true}\|_\infty &= \text{max}_{i=1..N} \left|u(x_i) - u_\textrm{true}(x_i)\right| \end{align*} Here, the $x_i$, $i=1,\ldots,N$ is a fixed uniform grid across the domain, not the collocation points, since these could vary in the convergence analysis and the PINN solve explicitly enforces the governing equation at the collocation points, so it is important that the norm measures the error at other locations. The scale factor $N^{-1/2}$ in the discrete $l_2$ norm ensures the norm approximates the continuous $L_2$ norm as $N$ gets large, rather than tending to $\infty$. In the below convergence study we will use $N=1000$.

Step 6: Numerical error convergence study¶

The next step of the workflow is to perform a convergence analysis. Important note: for PINNs (and other neural networks) 'convergence' usually refers to convergence of the loss during training. We will refer to that concept as 'training convergence', and in this notebook 'convergence' refers to convergence of the numerical solution to the true solution as numerical parameters are varied.

For (time-independent) FEM, there was one parameter, $h$, that was varied. The error theory provided expected orders of convergence in the error norms as a function of $h$. However, for PINNs there is no direct, single equivalent of $h$. For FEM, decreasing $h$ has two effects. First, it increases the size of the approximation space, that is, the function space the numerical solutions reside in. For example, decreasing $h$ for linear elements means the solution can be better approximated by a piece-wise linear function. Second, it can reduce total numerical integration error, since the integrals are computed using smaller elements. For the PINN, the size of the approximation space is determined by the network architecture, i.e. the number of layers and numbers of neurons per layer. The universal approximation theory for neural networks states that any function (satisfying certain conditions) can be approximated arbitrarily well by some sufficiently large neural network, but larger architectures may be needed to achieve very small numerical error. On the other hand, an analog of reducing FEM integration error is increasing the number of collocation points (training points), which increases the number of points the PDE is enforced at.

Overall, while the number of collocation points will need to be increased in the convergence analysis, convergence may eventually be limited by the fixed architecture being unable to approximate the true solution arbitrarily well. However, increasing the network size could result in overfitting, and increasing network size or number of collocation points can lead to training difficulties.

To explore numerical error convergence, the 1D PINN solver was run using a range of architectures and numbers of collocation points (10 to 640). The networks chosen were 2x20 (i.e., 2 layers, 20 neurons per layer; 481 trainable parameters), 4x10 (361 trainable parameters) and 4x20 (1321 trainable parameters). The solution training loss (PDE component), test loss (PDE solution), $l_2$ error and $l_{\infty}$ error were computed and saved to file. The following settings were used: num_epochs=100000, randomly sampled collocation points, learning rate decay switched on, and the model corresponding to the smallest test loss saved as the final result.

There are two sources of randomness that impact the results, the randomly selected collocation set and the random initialization of the network weights. Therefore, 5 replicates were run for each test, using 5 different seed values.

All results have been previously computed and are saved in the ../saved_results folder. The code used to generate these results can be found in scripts/generate_PINN_1d_convergence_results.py. Here, for the same problem, it is computationally expensive (requiring hours on a CPU, with GPU only providing limited speed-up for networks of these sizes) due to training expense and need for multiple replicates, and only achieves a limited decrease in error.

Reducing the maximum number of epochs from 100000 to 10000 led to larger final errors and stagnation, for all architectures. This shows how training error can dominate unless sufficiently long training is used. The results from the uniform collocation points are interesting, because the remaining randomness (network weight initial state) results in much narrower output bands for the final results, especially for the 4x20 network, and the clearest linear error convergence. However, immediate stagnation follows.

These results demonstrate how lack of error theory, training challenges and stochastic variability together mean that FEM-like quantification of numerical error against expected orders of convergence may not be feasible for PINNs, and even demonstrating clear numerical convergence can be challenging. Therefore, achieving a level of confidence in PINN implementations comparable to that obtained for traditional FEM solvers may require different verification strategies than those used for conventional methods. We propose the following new strategy, which is motivated by the relative simplicity of the differential equation-specific code in PINN implementations compared to finite element codes.

First, structure a PINN solver so that it can solve both the full PDE of interest and a related simplified PDE, with minimal differences in the underlying implementation. The simplified problem can be selected such that training is expected to be less challenging while still exercising the shared PINN infrastructure (e.g., geometry construction, loss construction, residual evaluation, automatic differentiation, and boundary-condition handling). Empirical convergence analysis may then be feasible using the simplified problem. The full PDE implementation could additionally undergo targeted MMS-based testing, with detailed inspection of any code not exercised by the simplified problem. This could provide a practical, PINN-specific approach for establishing confidence in implementation correctness.

We demonstrate and test this idea using the second PINN solver: a solver of the monodomain equations on the unit square. The monodomain equations govern the propagation of electric potential in an excitable medium such as heart tissue, and underlie many cardiac electrophysiological models that have various applications in cardiovascular devices. The monodomain equations are: \begin{align} \chi \left( {\cal C}_{m} \frac{\partial V}{\partial t} + I_{\mbox{\scriptsize ion}}(\mathbf{u}, V) \right) - \nabla \cdot \left( \sigma \boldsymbol{\nabla} V\right) & = I_{\mbox{\scriptsize stim}}, \\ \frac{\partial \mathbf{u}}{\partial t} & = \mathbf{f} \left( \mathbf{u},V \right) \end{align} where the unknowns are the transmembrane voltage $V(\mathbf{x},t)$ and a vector of cellular state variables $\mathbf{u}(\mathbf{x},t)$. The parameters are the surface-area-to-volume ratio $\chi$, the membrane capacitance ${\cal C}_m$, and the tissue conductivity tensor $\sigma$. $I_{\mbox{\scriptsize ion}}(\mathbf{u}, V)$ is the ionic current, $I_{\mbox{\scriptsize stim}},$ the stimulus current and $f\equiv f(\mathbf{u}, V)$ the cell model right hand side term that governs rate of change of the cellular state variables. Various cell models (specific choices of $I_{\mbox{\scriptsize ion}}$ and $f$) have been proposed; see Trayanova, 2024.

The function PINN_monodomain_solver provides a PINN monodomain solver analogous to the 1D elliptic equation solver. It assumes the domain is the unit square $[0,1]\times[0,1]$, and the cell model has three states. The default collocation point distribution uses Hammersley sampling. Initial conditions are imposed as a hard constraint (essentially writing $V(\mathbf{x},t) = V_0(\mathbf{x}) + t \hat{V}(\mathbf{x},t)$ and solving for $\hat{V}$).

Monodomain implementations can be tested using the MMS-derived test problems of Pathmanathan, 2014. Here we solve the monodomain 2D test problem of Pathmanathan, 2014, which provides parameter values, initial and boundary conditions, and a non-physiological three-state cell model such that the exact solution on the unit square is \begin{align} V(x,y,t) &= (1+t)^{1/2}\cos(\pi x)\cos(2\pi y)\\ u_1(x,y,t) &= (1+t)(1+xy^2) + (1+t)^{1/2}\cos(\pi x)\cos(2\pi y)\\ u_2(x,y,t) &= (1+t)^{-1}(1+xy^2)^{-1/2}\\ u_3(x,y,t)&=0 \end{align} A problem class MonodomainMMSProblem defines this test problem. Below the test problem is solved using 10000 epochs and default values for other inputs, and the solution and error are plotted at $t=0$, $0.5$ and $1$.

To test the above strategy we set up a second, simplified, test problem by setting the ionic current to zero and uncoupling the ODEs ($f_i = f_i(u_i)$ only), thus reducing the monodomain equation to a heat equation. Parameters and cell-model right-hand side were chosen so the exact solution is $V(x,y,t)=e^{-2.3t}\cos(\pi x)\cos(\pi y)$, $u_1=1.1t$, $u_2=e^{-1.2t}$ and $u_3=0$. A second problem class (from PINN_monodomain import HeatEquationProblem) can be passed to the PINN solver to solve this heat equation test problem.

Convergence studies for the simplified heat and full monodomain problems were performed using a 2x32 network, increasing numbers of collocation points, five random seeds, both 10000 and 50000 training epochs and otherwise default training parameters. Error was quantified as a sum of normalized time-averaged spatial-$L_\infty$ errors: $E=\frac{1}{N_t}\sum_{k=1}^{4}\sum_{j=1}^{N_t}\frac{\left\|U_k(\cdot,t_j)-U_{k,\mathrm{true}}(\cdot,t_j)\right\|_{l_\infty}}{S_k}$, where the $U_k$ represent the four unknowns $V$, $u_1$, $u_2$, $u_1$ and $N_t=11$. The normalization factors $S_k$ were chosen to be the maximum absolute true solution of $U_k$ over all $x$ and $t$, except $S_4=1$ as $u_3=0$ for both problems. The code for generating these results can be found in scripts\generate_monodomain_results.py. The results are shown below:

The results provide partial support for this strategy. The trends are not markedly different between the two problems. A clearer separation - for example, stagnation for the monodomain MMS problem but clean convergence for the heat equation - would have provided stronger support. However, the heat equation errors are substantially lower than those for the full monodomain MMS problem. In fact, errors after 10K epochs for the heat equation are lower than those for the full monodomain problem after 50K epochs. The monodomain problem also showed slightly greater stagnation, with median errors increasing at the highest collocation level. These results suggest that, had the computational budget been limited, a simplifed problem convergence analysis (e.g., heat equation 10K results), together with targeted testing of the full problem (e.g., one of the higher resolution monodomain 50K results), could have provided an efficient approach for establishing confidence in solver implementation.

Calculation verification¶

The above analyses address code verification: establishing confidence that the PINN solver is implemented correctly. They do not establish that a particular trained PINN has sufficiently small numerical error for a specific application. This distinction is especially important for PINNs because, as seen in the results above, numerical accuracy can depend strongly on network architecture, collocation points, training duration, optimization settings, the problem being solved, as well as stochastic factors. Numerical error for specific simulations is assessed in the calculation verification stage, which is outside the scope of this notebook; however, we note that the results above emphasize the importance of calculation verification for PINN-based numerical solutions.
